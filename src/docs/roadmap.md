# Objective:
Create a Node.js CLI tool for "vibe coding" and development assistance. This tool will run locally in terminal environments (Linux, macOS, WSL, Git Shell in Windows). The core functionality involves loading a specified folder's content, storing it as embeddings in a local SQLite database using the `sqlite-vec` extension, and allowing users to ask questions about the loaded content, with answers generated by a chosen LLM (OpenAI, Anthropic, or Gemini).

Key Requirements & Features (Points 1-10):

1.  **CLI Tool & Platform Compatibility:**
    *   Build with Node.js.
    *   The main script should be executable (e.g., using `#!/usr/bin/env node`).
    *   Ensure it can be developed in standard Node.js environments (including cloud-based IDEs like Google Cloud Shell Editor if desired) but runs as a local CLI.
    *   It should be compatible with Linux, macOS, WSL, and Git Shell (MinGW).

2.  **Input Handling:**
    *   The CLI must support:
        *   Commands starting with a forward slash (e.g., `/load <path>`).
        *   Normal prompts for data input (e.g., asking for a folder path if not provided as an argument).
        *   Interactive choices/menus (e.g., for selecting an LLM provider if not configured or for confirmations). Use the `inquirer` library for this.
    *   The main interaction should be through a persistent CLI prompt (e.g., `> `).

3.  **Input Validation & Responses:**
    *   Validate all user inputs (command syntax, file/folder paths, option choices).
    *   Provide clear, user-friendly feedback for valid inputs, errors, and command execution status. Use the `chalk` library for colored output.

4.  **Folder Loading & Embeddings (`sqlite-vec` - Vanilla Implementation):**
    *   **Command:** Implement a `/load <folder_path>` command.
    *   **File Handling (Custom/Vanilla):**
        *   Recursively scan the specified `folder_path`.
        *   Identify and read content from relevant file types (e.g., `.js`, `.ts`, `.py`, `.md`, `.txt`). Make the list of processable extensions configurable or easily extendable.
        *   Implement a mechanism to ignore common non-content directories/files (e.g., `node_modules`, `.git`, `dist`, `.DS_Store`, `package-lock.json`) and files and folders of .gitignore.
    *   **Chunking Strategy (Custom/Vanilla):**
        *   Implement a custom text chunking strategy *without using Langchain's text splitters*.
        *   **For text files (.md, .txt):**
            1.  Attempt to split by paragraphs (e.g., two newlines).
            2.  If paragraphs are too large (e.g., > 1500 characters), split them by sentences (use a simple regex for sentence boundaries).
            3.  If sentences are still too large, split by a fixed number of characters (e.g., 1000 characters) with a small overlap (e.g., 100 characters).
        *   **For code files (.js, .py, etc.):**
            1.  Attempt to split by lines.
            2.  Group lines into chunks of a configurable maximum size (e.g., 50-100 lines or ~1500 characters).
            3.  Consider simple regex-based splitting for functions/classes as a more advanced option if feasible within "vanilla," but prioritize simpler line/character-based chunking first.
        *   Each chunk should store its original file path as metadata.
    *   **Embedding Generation:**
        *   For each chunk, generate an embedding vector using the currently configured LLM provider's embedding model (see point 6).
    *   **SQLite & `sqlite-vec` Storage:**
        *   Use the `sqlite3` Node.js library and the `sqlite-vec` extension.
        *   Provide clear instructions on how to ensure `sqlite-vec` (e.g., `vector0.so`/`.dylib`/`.dll`) is available and loaded by the application.
        *   Define a SQLite schema:
            *   `documents` table: `id (PK)`, `file_path (TEXT)`, `chunk_text (TEXT)`, `created_at (DATETIME)`.
            *   `vec_documents` virtual table (using `vec0`): `embedding (FLOAT[DIMENSION])`. `rowid` should link to `documents.id`. The `DIMENSION` must match the embedding model's output.
        *   Store the original chunk text, its source file path, and its embedding vector.

5.  **Q&A Functionality:**
    *   **Command:** Implement a `/c <question>` (or `/ask <question>`) command.
    *   **Process (Custom/Vanilla):**
        1.  Take the user's `<question>`.
        2.  Generate an embedding for the question using the configured embedding model.
        3.  Query the `vec_documents` table in SQLite to find the top K (e.g., K=5) most similar chunks using vector similarity search (`MATCH` operator with `sqlite-vec`).
        4.  Construct a detailed prompt for the chosen LLM. This prompt should include:
            *   A system message defining the AI's role.
            *   The retrieved context chunks, clearly demarcated (e.g., "Context from file X: [chunk_text]").
            *   The user's original question.
        5.  Send the constructed prompt to the configured LLM's chat completion API.
        6.  Display the LLM's response to the user. Use `ora` for spinners during LLM calls.

6.  **LLM Integration (Multi-Provider - OpenAI, Anthropic, Gemini):**
    *   **Configuration:**
        *   LLM API keys must be loaded from a `.env` file (e.g., `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`).
        *   A JSON configuration file, `src/config/settings.json`, will determine the active LLM provider and models. Example structure:
            ```json
            {
              "activeProvider": "openai", // "openai", "anthropic", "gemini"
              "llmModels": {
                "openai": {
                  "chatModel": "gpt-3.5-turbo",
                  "embeddingModel": "text-embedding-3-small",
                  "embeddingDimension": 1536
                },
                "anthropic": {
                  "chatModel": "claude-3-haiku-20240307", // Or other Claude models
                  "embeddingModel": null, // Anthropic doesn't have a separate public embedding API as of last check, use OpenAI/Gemini for embeddings or note this limitation. If they do, specify.
                  "embeddingDimension": null // If applicable
                },
                "gemini": {
                  "chatModel": "gemini-1.5-flash-latest", // Or other Gemini models
                  "embeddingModel": "text-embedding-004", // Or other Gemini embedding models
                  "embeddingDimension": 768
                }
              }
            }
            ```
        *   The application should read this config at startup.
    *   **SDK Usage:**
        *   Use the official Node.js SDKs: `openai`, `@anthropic-ai/sdk`, `@google/generative-ai`.
    *   **Abstraction:** Create a simple abstraction layer or utility functions to:
        *   Get an embedding for a given text, dynamically using the SDK and model specified in `settings.json`.
        *   Send a chat completion request (with prompt/messages), dynamically using the SDK and model specified in `settings.json`.
        *   Ensure the correct embedding dimension is used for `sqlite-vec` based on the active embedding model.

7.  **Help Command:**
    *   Implement a `/?` (or `/help`) command that displays a list of available commands, their syntax, and a brief description.

8.  **Tech Stack:**
    *   Node.js.
    *   Plain JavaScript with JSDoc for documentation and type hinting.
    *   No Langchain or other high-level AI orchestration frameworks. All core logic for document processing, chunking, embedding management, and LLM interaction should be custom.

9.  **UI/UX Enhancements:**
    *   Use `chalk` for colored and styled terminal output.
    *   Use `ora` for spinners during long-running operations (e.g., loading folder, API calls).
    *   Use `figlet` for an ASCII art title at startup.
    *   Optionally, use `boxen` for framing important messages or `cli-table3` for displaying structured data (e.g., a list of loaded files, if implemented).

10. **Command Differentiation:**
    *   Primary command syntax: `/<command> <arguments>`.
    *   Consider simple aliases if appropriate (e.g., `/h` for `/help`).

11. **Dev scripts**
    * Add linter rules and command in package.json, prettier and command in package.json, and unit test using jest and command in package.json.

Deliverables:

*   A clear file structure for the Node.js project.
*   The JavaScript code for the CLI tool, well-commented with JSDoc.
*   An example `src/config/settings.json` file.
*   An example `.env.example` file.
*   Clear instructions on:
    *   Project setup (dependencies).
    *   Compiling/obtaining and placing the `sqlite-vec` extension.
    *   Running the CLI tool.
    *   How to configure LLM providers and API keys.
Please be specific about the vanilla implementations for chunking and LLM interaction logic.
The primary goal is a functional local CLI tool meeting these requirements, built from fundamental Node.js modules and the specified libraries.
